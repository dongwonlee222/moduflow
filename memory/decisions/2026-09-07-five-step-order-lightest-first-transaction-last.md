# 순서 — 가벼운 것부터, 트랜잭션은 마지막

## Summary

```
1. 151  spec-kit을 켤 수 있게        ← 코드를 안 지우고 5,786줄을 살린다
2. 150  이슈 번호 중복 거부
3. 139  안 불리는 6,735줄을 읽는다   ← 지우기 전에 읽는다
4. p0   105 · 133 · 141             ← 목표 완료 조건 ②
5. 132  트랜잭션 11,691줄           ← 가장 크다. 마지막
```

## Rationale

- **1·2는 작고 확실하다.** 먼저 끝난다.
- **3은 읽기만 하므로 안전하고**, 4·5의 근거가 된다.
- **4는 목표 자체다** — 완료 조건 ②(다른 사람·다른 컴퓨터가 받아도 똑같이 동작).
- **5는 가장 크다.** 1~3이 무엇을 바꿀지 모르는 상태에서 손대면 다시 하게 된다.

**1이 첫 번째인 이유**: 코드를 한 줄도 안 지우고 5,786줄의 성격을 바꾼다.
**쓰면 무게가 아니다.** 지우는 것보다 낫다.

## Evidence

실측 2026-09-07:

| | 줄 | 비중 |
|---|---|---|
| 트랜잭션 두 파일 | 11,691 | scripts의 26% |
| 아무도 안 부르는 14개 | 6,735 | 15% |
| spec-kit 전용 | 5,786 | 13% |

- 끝난 이슈 117건으로 나누면 **이슈당 383줄**이다.
- 가장 큰 커밋 7개를 합쳐도 **19%**다 — 한 방이 아니라 **누적**이다.
- `specs/` 60,415줄 중 **97%가 끝난 이슈의 기록**이다. "저장소가 무겁다"의
  절반은 코드가 아니라 이력이다.

## Alternatives

- **p0 먼저** — "가벼워지기"에 답하지 않으므로 뒤로.
- **132 먼저** — 132의 Scope In이 전부 *추가*라 오히려 커진다. 그리고 1~3 전에
  하면 두 번 하게 된다.
- **안 읽고 지우기** — `151`에서 배운 것이 정확히 그 위험이므로 기각.

## Reversal Conditions

**3단계 결과가 이 순서를 바꿀 수 있다.** 6,735줄이 거의 다 살릴 수 있는 것으로
나오면 5단계의 전제(무게를 줄여야 한다)를 다시 본다. 반대로 거의 다 죽은 것이면
5단계 앞에 "지우기" 단계가 하나 생긴다.
