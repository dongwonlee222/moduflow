# Design: Project-Aware Production Library Dashboard

Issue: `086-project-aware-production-library-dashboard`
Status: approved
Approved by: Dongwon Lee, 2026-07-10
Source spec: `specs/086-project-aware-production-library-dashboard/spec.ko.md`
Prototype: `specs/086-project-aware-production-library-dashboard/prototype.html`

## Design Decision

Extend the existing generated ModuFlow dashboard without redesigning its visual language. Preserve the current title, system font, blue active tabs, rounded filter controls, white table, borders, badges, and bottom information panel. Add only the project-aware controls and production-knowledge views required by Issue 086.

The approved Production Record detail interaction is a dimmed modal, not a persistent right panel. This keeps the existing full-width table intact and provides enough space for long production history.

## Existing Implementation Preservation Contract

The implementation baseline is the current `memory/dashboard.html` generated by `scripts/project_memory.py`, not a visually similar reimplementation.

- Preserve Issue 056's full Issue DB collector, search, status chips, sorting, grouping, artifact badges, attention flags, and issue-detail navigation.
- Preserve Issue 045's Cytoscape issue/knowledge graphs, status/kind colors, goal compound nodes, relationship toggle, knowledge badges, node motion, click previews, cross-graph navigation, and `#issues` / `#memory` deep links.
- Preserve Issue 047's generated issue/memory detail links and Korean sidecar behavior.
- Do not simplify or rebuild existing collectors, node/edge payloads, graph layouts, or hash routing merely to add the new tabs.
- Regression verification compares the real generated dashboard before and after the extension.

## Visual Foundation

- Font: `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif`; macOS renders SF Pro.
- Page: white background, 20px page padding, compact 19px title.
- Tabs: existing rounded neutral buttons; active tab uses `#2a78d6` with white text.
- Containers: existing 1px `#ddd` borders and 8px radius.
- Table: existing compact header, row borders, and blue-tinted hover/selection state.
- Status: existing badge and chip shapes; green indicates approved/current reusable guidance, amber indicates review.
- Dark mode: retain the existing `prefers-color-scheme` behavior when implemented.

No new brand header, KPI-card row, sidebar, decorative gradient, or unrelated navigation system is introduced.

## Screen Structure

### Title Row

The existing `ModuFlow 프로젝트 뷰` title remains in the top-left. A compact `프로젝트` select control is added at the top-right.

Project names must never be hardcoded examples. Single-project mode reads `.moduflow/config.json` or the project profile. Portfolio mode reads only registered entries from `portfolio/projects.json`.

The current ModuFlow repository registers only `moduflow / ModuFlow`, so its prototype shows a disabled `ModuFlow` selector. Selection and `전체 프로젝트` become available only when two or more projects are registered.

### Navigation

Keep the existing tabs and append two views:

1. 이슈 DB
2. 이슈 그래프
3. 지식 그래프
4. 제작 기록
5. 플레이북

The generated timestamp remains right-aligned on the same line when space permits and wraps below on mobile.

### Project Summary

A single compact summary line appears below the tabs. It reports only operational context for the selected project: active/review counts, Production Record count, Playbook count or review candidates, and next command.

`전체 프로젝트` shows aggregate counts and attention only. It never renders Production Record bodies, internal copy, or merged project knowledge.

### Production Records

Use the existing `.db` and `.dbbar` patterns.

- Search spans title, decision, failure, and reusable pattern text.
- Status uses existing rounded chips: 전체, 승인, 검토, 완료.
- Type uses the existing select style.
- The table remains full width with columns for Production Record, Type, Channel, Status, and Playbook.
- Row selection uses the existing blue-tinted hover/selected treatment.

The initial implementation may add channel, audience, lifecycle, and playbook-state filters as selects when real fixture volume justifies them. Controls must wrap instead of shrinking below readable widths.

## Production Record Modal

Clicking a Production Record row opens a centered modal over a 42% black dim layer.

- Desktop width: maximum 880px with 32px viewport margins.
- Desktop height: maximum viewport height minus 64px; modal body scrolls.
- Mobile: full viewport width, maximum 92vh, anchored to the bottom with rounded top corners.
- Close methods: close button, dim-layer click, and Escape key.
- Focus moves into the modal on open, remains trapped while open, and returns to the originating row on close.
- Background content does not scroll while the modal is open.
- URL detail state uses `replaceState`; project and primary view navigation use `pushState`.

The modal displays:

1. title, date, type, channel, audience, and lifecycle status
2. Artifacts
3. Source Inputs
4. Decisions
5. Failed Attempts
6. Reusable Patterns
7. Do Not Repeat
8. external/customer-facing copy
9. internal reporting copy
10. Playbook Updates and source links

External copy and internal reporting copy use separate bordered blocks so neither can be mistaken for the other.

## Playbooks

The Playbooks tab reuses the same `.db` table pattern. It shows scope, version, approval status, approver/date, review state, and source-record count.

Only `approved` Playbooks receive the green reusable-guidance treatment. Candidates and deferred items remain visibly review-only and cannot look like current policy.

Opening a Playbook uses the same modal shell, with source Production Record links and supersession history.

## Project Switching

One `selectedProjectId` controls every view. Changing the project performs one atomic transition:

1. validate the registered project ID
2. close open issue, record, playbook, and memory details
3. reset filters that are invalid for the target project
4. replace the header summary and all view payloads
5. render the active view
6. update `?project=<id>#<view>`

No tab owns an independent project selection.

## States

- Missing portfolio registration: current project mode remains usable; portfolio guidance appears only when requested.
- Unreadable project: show a non-blocking warning for that project and retain other registered projects.
- Empty Production Records or Playbooks: render the existing empty-panel pattern with the relevant ModuFlow registration command.
- Removed URL project: fall back to the default project and show a visible warning.
- Missing artifact: keep the record visible and show an attention flag.
- Truncated project payload: display generated-at, retained count, omitted count, and regeneration guidance.

## Responsive Behavior

- Title and project selector stack on narrow screens.
- Tabs and summary wrap without clipping.
- Filter controls become one column when required.
- Production tables remain horizontally scrollable instead of compressing text into unreadable cells.
- Record and Playbook details use the mobile modal described above.
- No fixed pixel font scaling based on viewport width.

## Accessibility

- Tabs are buttons with active-state semantics.
- Project and filter controls have visible labels or accessible names.
- Tables preserve header associations.
- Modal uses `role="dialog"`, `aria-modal="true"`, and a title reference.
- Keyboard interaction covers Enter/Space on rows, Escape close, focus trap, and focus return.
- Status meaning is communicated by text as well as color.

## Validation

- Desktop screenshots: Issue DB unchanged, Production Records table, open Record modal, Playbooks table, `전체 프로젝트` summary.
- Mobile screenshots: stacked title/project control, wrapped tabs/filters, table scroll, bottom-anchored modal.
- Interaction checks: project switch, URL restoration, invalid project fallback, filter reset, modal open/close/focus, empty state, missing artifact warning.
- Regression checks: existing Issue DB, issue graph, knowledge graph, and issue drill-down remain functional.
- Current observed baseline: 87 issue nodes / 198 issue edges and 14 knowledge nodes / 4 knowledge edges. Tests compare generated before/after equivalence rather than permanently pinning those changing counts.
- Issue DB must render the full `issues/*.md` collector result, not representative sample rows.
- Displayed project names must match `.moduflow/config.json` and `portfolio/projects.json`.
- Required commands: focused dashboard tests, project validation, and `python3 scripts/release_check.py .`.

## Rejected Alternatives

- Persistent right detail panel: reduces the existing full-width table and changes the established layout too much.
- New branded application shell: visually disconnects the new views from the current ModuFlow dashboard.
- Separate detail page for every record: good for long reading but slower for repeated list review.
- Browser write-back: remains outside v1 because it requires Git conflict, authorization, validation, and commit semantics.

## Approved Outcome

The approved direction is the existing ModuFlow UI plus a global project selector, Production Records and Playbooks tabs, and dimmed modal details. The prototype intentionally demonstrates this incremental extension rather than a visual redesign.

The prototype is now based on the real generated ModuFlow dashboard. It does not redraw the Issue DB or graphs with sample data. Because this repository has no registered Production Records or approved Playbooks, those tabs show truthful empty states.
