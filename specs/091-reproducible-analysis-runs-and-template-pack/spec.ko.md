# 명세(요약): 재현 가능한 분석 실행과 템플릿 팩

Issue: `091-reproducible-analysis-runs-and-template-pack` · 담당/결정: 이동원
단계: 검토용 초안, 2026-09-03 개정 2판. 이 문서는 구현·상태 전환·배포·설치를 승인하지 않는다.
정본: 영문 [spec.md](spec.md). 이 사이드카는 검토 편의용 요약이며, 충돌 시 영문이 우선한다.

## 왜 필요한지

같은 요청을 매번 다시 설명하고 있다. 매주 도는 이용 분석도, 가끔 들어오는 정책 영향 분석도 똑같은 걸 다시 말해야 한다 — 어떤 모집단, 어떤 기간, 어떤 검증, 어떤 문서 형식, 어떤 승인된 문구. 그걸 프로젝트별·작업물별로 들고 있는 자리가 저장소에 없어서, 재사용되지 않고 매번 다시 말해진다.

## 해결해야 할 문제

1. **결론을 다시 도출할 수 없다.** 이전 실행의 원본 탭, 추출 시각, 제외 규칙, 쿼리가 남지 않아 같은 분석이 다른 숫자를 낸다.
2. **입증되지 않은 주장이 입증된 것처럼 읽힌다.** 완료·검증·승인·성숙 대기가 한 덩어리다. 모르는 비용이 0으로 읽히고 추세가 인과로 읽힌다.
3. **문서 형식과 승인된 문구가 흔들린다.** `moduflow.playbook.v1`에 승인 카피와 승인 구조가 이미 있는데, 분석 실행과 연결돼 있지 않아 실제로는 강제되지 않는다.

## 기대 효과

- 같은 작업물의 **두 번째 실행은 기간만 말하면 된다.** 나머지는 playbook이 채운다.
- 나중 실행이 이전과 무엇이 왜 다른지 말할 수 있다.
- 완료·검증·승인·결정 대기가 분리되어, 검증도 승인도 없는 숫자가 근거로 쓰이는 일을 줄인다.
- 매주 리포트와 비주기 리포트가 같은 playbook을 쓰는지 강제된다.

측정된 개선치는 아직 없다. 위는 기대 효과다.

## 핵심 구조

- 분석 실행은 `workspace/analysis-runs.md`에 누적으로 쌓인다. 파서는 하나다.
- 작업물의 계약(프로세스 참조, 필수 검증 체크리스트, 승인 카피·구조)은 **기존 playbook**이 들고 있다. 새 템플릿 체계를 만들지 않는다.
- 프로젝트 playbook이 기본 playbook을 이름으로 덮어쓴다. 새 이름이면 그냥 늘어난다.
- 출처는 090의 `(artifact_id, snapshot_commit)`으로 고정한다. 등록도 090 경계를 쓴다.
- 쓰기는 103 트랜잭션의 한정된 intent 하나로 처리한다.

## 기존 요구 ↔ 추가 요구

기존 요구 중 **누락된 것은 없다.** 다섯 템플릿(E3)은 기본 playbook 다섯 개로 그대로 간다. 의미가 바뀐 건 E5 하나로, 자유 텍스트 링크가 ID 참조로 좁혀진다.

추가 요구 중 **A1(회사→프로젝트→이슈 프로필 체인)은 이번에 미룬다.** 전제가 되는 외부 회사 표준 문서가 아직 없고, 이번 불편과 무관하며, 나중에 playbook 필드 하나로 붙일 수 있다. 나머지 추가 요구는 전부 반영했다.

## 하지 않는 것

계산 엔진·노트북·SQL 실행기·차트 렌더러·크롤러·DB·lineage 엔진·업로드 없음. 스케줄러·큐·타이머·자동 재실행 없음 — **매주 저절로 도는 일은 없다.** 회사 데이터/지표값/원가식/KPI/자격증명 저장 없음. 두 번째 등록부·파서·트랜잭션 엔진·템플릿 체계 없음. 문서 생성 프레임워크 없음. 승인 화면·승인 흐름 없음 — 승인은 날짜와 링크 한 줄이다. 조직 공유는 107, 최종 상태 게이트는 108, UI는 092가 소유.

## 완료 기준은 데모다

테스트 통과가 기준이 아니다. 합성 프로젝트에서 주간 분석 playbook을 만들고, 한 번 실행하고, **두 번째에 기간만 말했는데 같은 형식으로 나오는지**를 관측해 기록한다. 이게 안 되면 나머지가 다 통과해도 목적을 달성하지 못한 것이다.
